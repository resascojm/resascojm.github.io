🏢 Pilot CRM

Es el sistema donde los vendedores de Guspamar cargan todo: ventas, leads, clientes, stock. Tiene dos puertas de entrada: la web (la que usás vos con tu usuario) y la API (una puerta para programas, no para personas).

⚠️ Detalle clave: la API de Pilot no acepta cuentas vinculadas a varias concesionarias a la vez. Por eso tu usuario personal sirve para la web pero la API lo rechaza.

🔌 Conector MCP de Pilot

Es el "enchufe" que me deja consultarle cosas a Pilot directamente desde el chat: "traeme las ventas de junio", "buscá tal cliente". Alguien lo configuró una vez con credenciales válidas, que quedan guardadas de forma segura — ni vos ni yo las vemos.

✅ Ideal para consultas puntuales. ❌ No sirve para bajar un año entero de datos: el chat se desborda.

📜 La skill dashboard-guspamar

Es la "receta" guardada que sabe armar tu informe: qué datos bajar, las reglas de negocio (los 11 vendedores tradicionales, el filtro 0km, las exclusiones, la segmentación Ranger), y cómo generar el HTML final.

El corazón es un script de Python (generar_dashboard.py) que hace todo de una: se autentica en Pilot, baja los datos del año, los procesa y escupe el dashboard.

📦 El sandbox

Una computadora virtual aislada (Linux) donde corren los scripts. Está aislada a propósito: lo que corre ahí no puede tocar tu PC ni hacer cualquier cosa en internet. Tiene su propia salida a internet con una lista de sitios permitidos.

⚠️ Hoy el problema doble fue: primero no arrancaba (la VM estaba caída), y después resultó que api.pilotsolution.net no está en su lista de sitios permitidos.

🔑 Las credenciales

El script necesita dos datos para entrar a Pilot: PILOT_USER y PILOT_PASSWORD (usuario y contraseña, guardados como "variables de entorno" — una especie de cajita de configuración de la compu).

No puede usar tu usuario personal (la API lo rechaza por estar en varias instancias). Necesita un usuario de API dedicado, vinculado solo a Guspamar. Encontramos el candidato: pluginleads.resasco@myworkplace.com.ar — falta la contraseña correcta.

🔒 Buena práctica: las contraseñas nunca van por el chat. Se configuran una vez en el entorno y listo.

¿Por qué no usar siempre el camino del chat?

Por volumen. El chat es como pasarse mensajitos: bárbaro para preguntas puntuales. El dashboard necesita miles de registros desde enero — eso es un camión de mudanza, no un mensajito. Para eso está el script, que mueve todo afuera del chat y solo te muestra el resultado final.

Y la llave del conector no se puede "prestar" al script: está guardada a propósito donde nadie la puede leer. Es una medida de seguridad, no una traba caprichosa.

La historia del debugging, paso a paso

Tocá cada hito para ver el detalle. Así fuimos descartando causas.

1. La tarea del lunes falló: el sandbox no arrancaba▶
La computadora virtual donde corre el script no levantó (VM service not running). Sin ella, no hay dónde ejecutar Python. Dos lunes seguidos pasó lo mismo.
2. Reintentamos juntos: el sandbox revivió▶
Al probar de nuevo, la VM arrancó bien: Python 3.10 disponible y el script de la skill en su lugar. Primer obstáculo superado (era transitorio).
3. Pero faltaban las credenciales▶
Las variables PILOT_USER y PILOT_PASSWORD estaban vacías en el entorno. El script no tiene con qué autenticarse.
4. Probamos tu usuario personal: la API lo rechazó▶
Pilot respondió: Accounts with multiple Pilot instances linked can not be used for API authenticate. Traducción: tu cuenta está vinculada a varias concesionarias del grupo y la API solo acepta cuentas de una sola. No es problema de contraseña.
5. Descubrimos otro bloqueo: la red del sandbox▶
Al intentar conectar desde el sandbox, el proxy devolvió 403 Forbidden: api.pilotsolution.net no está en la lista de sitios permitidos. Las pruebas siguientes las hice por otra vía de red que sí funciona.
6. Probamos un usuario "api.pilot@...": no existe▶
Tres combinaciones, todas user_not_found. Ese usuario no figura en Pilot. Dato útil: tu usuario daba un error distinto, o sea que el mensaje de error nos dice mucho.
7. Encontramos el usuario correcto… falta la contraseña▶
pluginleads.resasco@myworkplace.com.ar SÍ existe: ahora el error es Incorrect password. Estamos a una contraseña de distancia. Las que probamos no son.

Moraleja

Cada error nos acercó: VM caída → sin credenciales → usuario rechazado → red bloqueada → usuario inexistente → usuario OK, contraseña no. Leer el mensaje de error exacto es el 80% del trabajo.

Checklist para que el lunes corra solo

🔑
1. Conseguir la contraseña de pluginleads.resasco@myworkplace.com.ar
Preguntale a quien configuró el conector MCP de Pilot, o reseteala desde Pilot web → Configuración → Usuarios. Es lo único que falta del lado de credenciales.
📦
2. Guardar las credenciales como variables de entorno
Que PILOT_USER y PILOT_PASSWORD queden configuradas en el entorno, no pasadas por el chat. Así la tarea automática las encuentra sola cada lunes.
🌐
3. Habilitar api.pilotsolution.net en la red
Si Grupo Resasco usa plan Team/Enterprise de Claude, el Owner lo habilita en Admin settings → Capabilities. Si no, revisar la configuración de red de Cowork en los ajustes de la app.
🔒
4. Cambiar tu contraseña personal de Pilot
Quedó escrita en el chat de hoy. Mejor renovarla y no volver a mandarla por ningún chat.
✅
5. Probar una corrida manual completa
Antes del lunes, pedime "actualizá el dashboard de Guspamar" y verificamos juntos que el HTML salga bien (más de 50 KB, sin errores).

Plan B mientras tanto

Para consultas puntuales (ventas del mes, performance de un vendedor, leads por origen) el conector MCP funciona hoy mismo — pedímelo por chat y te lo saco al toque. Lo que no puedo por esa vía es regenerar el dashboard completo del año.

Glosario sin chamuyo técnico

Tocá cada término.

API — la puerta para programas▶
Como la web de Pilot, pero pensada para que la usen programas en vez de personas. En lugar de pantallas con botones, devuelve datos crudos. El script del dashboard habla con Pilot por acá.
MCP / Conector — el enchufe estándar▶
Un estándar para "enchufar" servicios externos (Pilot, Gmail, etc.) al chat de Claude. Cada conector guarda sus propias credenciales de forma segura y me deja hacer consultas en tu nombre.
Skill — la receta guardada▶
Un paquete de instrucciones + scripts que me enseña a hacer una tarea específica de tu negocio siempre igual. La de Guspamar tiene grabadas todas tus reglas: los 11 vendedores, el filtro 0km, las exclusiones, los targets.
Script — el robot que hace el trabajo pesado▶
Un programa (acá en Python) que ejecuta una secuencia de pasos sin intervención: autenticarse, bajar datos, calcular, generar el HTML. Corre afuera del chat para poder mover volumen.
Sandbox / VM — la pecera▶
Una computadora virtual aislada donde corren los scripts. Como una pecera: lo de adentro no puede tocar lo de afuera. Por seguridad, su salida a internet solo permite sitios de una lista.
Variable de entorno — la cajita de configuración▶
Un valor con nombre que queda guardado en la compu (ej: PILOT_USER). Los programas lo leen al arrancar. Sirve para no escribir contraseñas adentro del código ni pasarlas por chat.
Token — la pulsera del boliche▶
Cuando el script se autentica bien, Pilot le da un "token": un pase temporal para las consultas siguientes, sin mandar usuario y contraseña cada vez. Como la pulsera que te ponen en la entrada.
Proxy / lista de permitidos — el portero de la red▶
Todo lo que sale del sandbox a internet pasa por un portero que chequea una lista. Si el sitio no está en la lista (como hoy api.pilotsolution.net), devuelve 403 Forbidden y no te deja pasar.
403 / errores HTTP — los carteles del camino▶
Códigos estándar de respuesta: 403 = prohibido, 404 = no existe, 500 = se rompió el servidor, 200 = todo OK. Leerlos te dice exactamente dónde está el problema.
Tarea programada — el despertador▶
Una instrucción que se ejecuta sola en un horario fijo — tu dashboard de los lunes. Para que funcione sin vos, todas las piezas (credenciales, red, sandbox) tienen que estar en orden de antemano.
